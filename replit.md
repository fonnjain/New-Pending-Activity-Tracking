# Balance & Activity Tracker

A mobile-first web app for steel-fabrication workshops. Upload an Excel (.xlsx or legacy .xls) balance/activity report and instantly see pending work, live ageing, contractor workload, and activity progress across five views.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server
- `pnpm --filter @workspace/tracker run dev` — run the frontend (use the workflow, not this directly)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- Frontend: React + Vite + Tailwind + wouter (artifact `tracker`, served at `/`)
- API: Express 5 (artifact `api-server`, served at `/api`)
- DB: PostgreSQL + Drizzle ORM
- Excel parsing: SheetJS (`xlsx`); uploads via `multer` (memory storage)
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)

## Architecture decisions

- **Append-only merge.** Each uploaded report = one immutable **import**; imports never replace each other (defaults to showing the newest = current state). Re-uploading is idempotent.
- **Two dedup layers, opposite intent.** WITHIN a file: NO dedup — in-sheet duplicate rows are preserved as separate pending units (tracked via `copies`, expanded in `/imports/{id}/records`). ACROSS uploads: dedup via a permanent `record_pool` keyed by full-row SHA-256 `hash`.
- **Per-import change log.** Each import stores a field-level diff vs the previous import: moved activity, qty/wt changed, new marks, completed. Change identity = `job|structure|markTail|jobCardNo`; a removed identity is flagged **completed**, never deleted. Pool rows are permanent; deleting an import cascades only `import_rows`.
- **Concurrency-safe uploads.** `POST /imports` takes `pg_advisory_xact_lock(728041)` so concurrent uploads serialize against a stable baseline; pool insert uses `onConflictDoNothing(hash)` + re-select.
- `ageingDays` is NOT stored — it is recomputed live (today − **Last Production Entry Date**, col S, the 19th source column) at read time, so ageing stays current without re-uploading. **Future production dates are clamped to today (ageing 0).** A blank/unparseable production date yields `ageingDays = null` (excluded from numeric buckets and averages everywhere). Null-ageing rows are labelled activity-aware: **"Not started"** when activity == `C` (cutting; production genuinely not begun) else **"No production date"** (progressed past cutting but date missing — a data-quality flag). `lastProductionDate` is stored on `record_pool` and is part of the row hash (col S participates in identity). The frontend display/label helpers live in `artifacts/tracker/src/lib/ageing.ts` (`ageingCell`/`noDateLabel`/`isCutting`); ageing math itself stays server-side (`computeAgeing` in parse.ts). The parse summary adds `notStarted`/`noProductionDate`/`futureProductionDate` counts, surfaced in the AI review signals. **NOTE: because col S now participates in the row hash, the first upload after this change shows a one-time re-identification churn (completed + new) vs older imports — not data loss.** `assignDate` is still parsed/stored/displayed (and still the date-range filter key) but no longer drives ageing.
- The parse summary (rowsRead, etc.) and change summary are stored as `jsonb` columns on the import because they cannot be reconstructed from the deduped pool.
- All KPIs, buckets, and breakdowns are computed client-side from the selected import's records with filters applied (AND logic). No separate aggregation endpoints.
- Deterministic self-checks (conservation: added+unchanged===rowsKept; idempotency; non-negative).
- **Optional advisory AI layer (never authoritative).** A bring-your-own-key Anthropic layer adds two read-only assists: sanitize (suggest descriptive-field cleanups) and review (audit computed results). It NEVER writes record_pool/import_rows/computed fields. **Sanitize is formatting-only for name fields:** a cleanup is dropped server-side (and `req.log.warn`'d) unless `from`/`to` share the same alphanumeric token sequence (lowercase, runs of non-alnum collapsed to one space, trim) — so whitespace/punctuation-spacing/casing fixes pass but suffix truncation/merges (e.g. "DASHMESH ENTERPRISES GP-2" -> "DASHMESH ENTERPRISES") are blocked. Enforced via `isTruncatingCleanup` (parse.ts) at all three paths (`/imports/validate`, `/imports/commit`, `/ai/sanitize`); `assignDate` and `lastProductionDate` are exempt (date normalization changes tokens — sanitize may suggest date-format-only fixes on these, never on activity). Both Claude prompts also forbid removing suffixes/units/branches/parentheticals/hyphenated tags. The key is read server-side only from `ANTHROPIC_API_KEY` (never sent to the browser, never logged). With no key the app works fully: `GET /ai/status` reports `available:false`, AI endpoints return `available:false`, and the UI disables the buttons with the note "Set ANTHROPIC_API_KEY to enable AI assists". Sanitize "Accept all" downloads a cleaned .xlsx (exact parse.ts layout) to re-upload — the engine recomputes; nothing is mutated server-side. Model ids live in `artifacts/api-server/src/lib/ai.ts`; AI routes in `artifacts/api-server/src/routes/ai.ts`; UI in `artifacts/tracker/src/components/ai-review-panel.tsx` and `ai-sanitize-panel.tsx`.

## Turnaround-time warning system (advisory, display-only)

- **Purpose.** The user configures an **ideal number of days per activity**; those ideal-days **accumulate down `PROCESS_SEQUENCE`** into a **cumulative target** for each activity (e.g. C=2, RFI=1, NH=3 → target C=2, RFI=3, NH=6). Each mark's **live ageing** is compared to its activity's cumulative target → an alert: **Green** (at/under target), **Yellow/Orange/Red** (increasing overrun beyond grace bands), or **na** (no defined target or no ageing). This is purely advisory — it NEVER changes parsing, Activity values, qty, dedup, or ageing math; it is recomputed live from settings exactly like activity ordering.
- **Engine (single source of truth): `@workspace/domain` (`lib/domain/src/index.ts`).** STORED model is **cell-based**: `GraceCell{mode:"auto"|"manual", percent?, value?}` (one grace band), `ActivityConfig{idealDays, yellow/orange/red: GraceCell}`, `PartialActivityConfig` (sparse per-cell override). `TurnaroundSettings{activities: Record<code, ActivityConfig>, perProject?: Record<project, Record<code, PartialActivityConfig>>}`. The **RESOLVED** numeric type `ActivityGrace{idealDays,yellowGrace,orangeGrace,redGrace}` is RETAINED — it is what every consumer (`alertStatus`/`cumulativeTarget`/status-dot/turnaround-warnings/reports) uses; nothing downstream sees cells. `resolveCell(cell, idealDays)`: manual → `value`; auto → `round((percent??0)/100 * idealDays)` (invalid/missing → 0). `resolveActivityGrace` resolves each band cell to numeric (per-cell: a project cell resolves vs the project's effective ideal, an inherited global cell vs global ideal) then `normalizeGrace`. `DEFAULT_ACTIVITY_CONFIG` (manual 7/21/21), `DEFAULT_TURNAROUND_SETTINGS`, `AlertStatus`, `AlertResult{status,target,overrun}`, `normalizeGrace`, `migrateTurnaroundSettings`, `cumulativeTargets`, `cumulativeTarget`, `alertStatus`. (Removed: `DEFAULT_ACTIVITY_GRACE`, `normalizePartialGrace`, `GRACE_FIELDS`.) Reuses the SAME `isKnownActivity`/`normalizeActivity` as the ordering layer (case-insensitive). `alertStatus` returns **`na`** whenever the target is null (activity outside `PROCESS_SEQUENCE`) OR `ageingDays` is null (blank production date) — never a false green/red.
- **Per-project overrides (additive — never changes target math, status bands, ageing, or n/a).** `activities` is the GLOBAL "All Projects" default; `perProject[project][activity]` holds SPARSE, PER-FIELD overrides (any subset of idealDays/yellow/orange/red). **Resolution is per-field:** `resolveActivityGrace(settings, project, step)` = global row with each overridden field replaced, then `normalizeGrace` (enforces yellow<=orange<=red on the merged row). `cumulativeTargets`/`cumulativeTarget`/`alertStatus` all take an **optional** `project` param — omit/null = global (back-compat). `cumulativeTarget(P,A)` sums the RESOLVED ideal-days for P. A project with no overrides behaves exactly like global. `migrateTurnaroundSettings` always emits a sanitized `perProject` (known activities only, non-neg ints, empty rows/projects pruned) and still accepts legacy flat shapes. The **project key is the record's `job`** field; every `alertStatus`/`StatusDot` call site passes `project: r.job`.
- **Per-activity grace bands as auto/manual CELLS (additive — replaced numeric storage, identical status math).** Each `PROCESS_SEQUENCE` activity stores `idealDays` plus three `GraceCell`s (yellow/orange/red). A cell is **MANUAL** (pinned `value` days) or **AUTO** (`value = round(percent/100 * THIS activity's idealDays)`, recomputed live whenever ideal days change). Both `percent` and `value` may coexist so toggling auto↔manual remembers the other. The cells are RESOLVED to numeric days (`resolveCell`) before any classification, so the **status calc is unchanged**: `target = cumulativeTarget(activity)`; if target null or ageing null → `na`; `overrun = ageing - target`; `overrun <= 0` Green; `<= yellowGrace` Yellow; `<= orangeGrace` Orange; else Red. **Red is terminal** (anything past Orange is Red); red is stored/validated/displayed only. `normalizeGrace` (runs on the RESOLVED numbers) rounds, clamps non-negative, and enforces `yellowGrace <= orangeGrace <= redGrace` (auto-correct by raising) — so even inverted percentages never invert the actual bands. `DEFAULT_ACTIVITY_CONFIG` = manual cells 7/21/21 (ideal 3). `migrateTurnaroundSettings` accepts the NEW cell shape, the PREVIOUS numeric `{yellowGrace,orangeGrace,redGrace}` shape (→ MANUAL cells, behaviour preserved), and the oldest flat `{idealDays,yellowMax,orangeMax,overrides}` shape (→ MANUAL cells, `red = orange`), so any stored row keeps behaving the same until a cell is opted into a percentage. **No `graceMode`/`yellowMax`/`orangeMax`/`overrides`.**
- **Persistence.** Singleton `settings` table (`lib/db/src/schema/settings.ts`): `activities` jsonb (global defaults) + `per_project` jsonb (sparse overrides, defaults `{}`) + id/updatedAt. `GET /settings` is **public** (read-only; migrates the stored row — both `activities` and `perProject` — via `migrateTurnaroundSettings` on read). `PUT /settings` **requires auth** (`requireAuth`), normalizes via `migrateTurnaroundSettings`, persists BOTH columns, and echoes back the SAME object it persists so the client cache never drifts. Route: `artifacts/api-server/src/routes/settings.ts`. **Note: prod DB must be re-pushed after deploying (the `settings` table added `per_project`) — run `pnpm --filter @workspace/db run push` against prod.**
- **Frontend.** Settings provider in `artifacts/tracker/src/lib/settings.tsx` (loads via `useGetSettings`, applies a local draft live, debounced `PUT` persist, reset). **On a settled save it reconciles local draft → the server's normalized response** (guarded by `saveTimer.current` so it never clobbers an in-progress edit), so the editor self-corrects inverted bands. Helpers (`ALERT_LABELS`, `statusTextColor`, `statusBgColor`) in `lib/turnaround.ts`. **All config inputs live on a dedicated auth-gated page `pages/warning-parameters.tsx` (`/warning-parameters`, wrapped in `<LoginGate>`, in the nav as "Warning Params"):** a **project dropdown** ("All Projects" = global, or a specific `job` from the selected import's records via `useGetImportRecords`) above a per-activity grid (ideal days input, RESOLVED cumulative target, and a yellow/orange/red **grace-cell editor** each). Each grace cell stacks a **days input** (Manual) over a **percent input** (Auto): the active mode is ring-highlighted, the other muted; editing days pins the cell to Manual, editing percent switches it to Auto (`value = round(percent/100 * idealDays)`), and a **"use %"** link reverts a manual cell to its stored percentage. Auto cells show an "auto" tag; inverted resolved bands surface a page-level "bands out of order" warning (the engine still auto-raises later bands, so status is never wrong). In **All Projects** mode the cells edit the full global `activities` rows (page-level "Reset to defaults"). In a **specific-project** mode the cells edit SPARSE per-cell overrides: an untouched cell inherits the global value (greyed placeholders, "inherited" tag), a touched cell is an override (ring-highlighted + per-cell **"inherit"** link to drop it); per-row **"Clear"** drops that row's overrides and page-level **"Reset this project"** drops all of them. Empty rows/projects are pruned client-side before persisting. **Overview (`pages/overview.tsx`) is RESULTS-ONLY** — the `turnaround-warnings.tsx` block (summary strip of Green/Yellow/Orange/Red/na counts, per-activity breakdown bars, Orange/Red drill table, respecting active filters) plus a link button to the config page. (The old inline `turnaround-settings.tsx` panel was deleted.) Consumers (`turnaround-warnings.tsx`, `reports.tsx`) defensively `migrateTurnaroundSettings(settings)` before classifying so a transient in-flight draft with inverted bands can never mislabel. Status colors are applied in the Ageing + Activity tables (via `components/status-dot.tsx`, alongside the fixed ageing scale which is kept). Reports + Excel export add `cumulativeTarget`/`overrun`/`alertStatus` columns. The `--ageing-orange` token (hsl 24 95% 53%) is in `index.css`. **The turnaround alert palette is display-only and INDEPENDENT of the fixed ageing scale** — it has its own `.status-*`/`.bg-status-*` classes in `index.css` (single source via `statusTextColor`/`statusBgColor` in `lib/turnaround.ts`): green=on-target (green), yellow=light blue (`hsl 200 90% 60%`), orange=grey (`hsl 0 0% 50%`), red=black (white text baked into `.bg-status-red`), na=faded slate with a hatched (striped) fill so a no-data n/a never looks like the solid grey orange. Changing these colors NEVER affects thresholds/status bands/cumulative targets/ageing — it is purely the rendered color. Do NOT reuse the `ageing-*` classes for status (they drive the days-based ageing buckets, which must stay green/amber/red).

## Proactive pre-warning + lifecycle ladder (additive overlay; advisory, display-only)

- **Purpose.** A THREE-STAGE PROACTIVE pre-warning layer sits ON TOP of the existing reactive breach alerts, giving an **8-state lifecycle**: `green` / `prewarn1` / `prewarn2` / `prewarn3` / `breach1` / `breach2` / `breach3` / `na`. Fully ADDITIVE — it does NOT change breach bands, cumulative-target math, ageing (=today − last_production_date), n/a handling, parsing, or dedup. `alertStatus` is UNCHANGED; the lifecycle is layered over it.
- **Engine: `@workspace/domain` (`lib/domain/src/index.ts`).** `lifecycleStatus(input, settings)` calls `alertStatus` first, then: if `na`/target null/ageing null → `na`. **Breach phase (overrun>0):** reuse the breach band verbatim — `yellow→breach1`, `orange→breach2`, `red→breach3` (`daysToTarget=0`). **Within-target phase (overrun<=0):** classify by **percent of cumulative target consumed** (`consumed = ageing/target*100`): `< pw1` green, `< pw2` prewarn1, `< pw3` prewarn2, else prewarn3. Returns `{status,target,overrun,consumedPct,daysToTarget}` where `consumedPct = round(ageing/target*100)` (null if target 0/na) and `daysToTarget = max(0, target − ageing)` (0 once breached, null when na). Types/consts: `LifecycleStatus`, `LIFECYCLE_ORDER`, `LifecycleResult`. **Pre-warn thresholds are %-only, per-activity, project-inherited exactly like grace cells:** `PreWarnConfig{pw1,pw2,pw3}` on `ActivityConfig` (defaults 70/85/95) + optional sparse `preWarn` on `PartialActivityConfig`; `resolvePreWarn(settings, project, step)` merges global+sparse per-field then clamps 0..100 and enforces pw1<=pw2<=pw3. `migrateTurnaroundSettings` seeds `preWarn` + `stalledDays` (accepts missing).
- **Stalled detection (cross-import, graceful).** A mark is **stalled** when its signature (sorted distinct uppercased activities `\u0002` sorted distinct lastProductionDates) has not changed for >= `stalledDays` (global, default 10; `DEFAULT_STALLED_DAYS`/`resolveStalledDays`). Backend `GET /imports/{id}/movement` (`routes/imports.ts`) walks prior imports newest→oldest and returns `{importId, hasHistory, items:[{markId, jobCardNo, daysSinceLastMovement}]}` — `daysSinceLastMovement` is null when no usable history (first appearance / no earlier import). Frontend hook `lib/movement.ts` (`useStalledInfo`) joins by identity `markId|jobCardNo` (`\u0001` sep), exposes `isStalled`/`daysFor`, and **never flags stalled when `hasHistory` is false** (degrades gracefully). `MovementItem`/`MovementResponse` schemas live in the OpenAPI spec (run codegen after edits).
- **Persistence.** `settings` table adds a `stalled_days` integer column (default 10); `GET/PUT /settings` read/write it. **Prod DB must be re-pushed after deploying** (`pnpm --filter @workspace/db run push` against prod).
- **Frontend.** Colour ladder classes `.lc-*`/`.bg-lc-*` (8 states) in `index.css`; helpers `LIFECYCLE_LABELS`/`LIFECYCLE_DESCRIPTIONS`/`LIFECYCLE_IS_PREWARN`/`LIFECYCLE_IS_BREACH`/`lifecycleBgColor`/`lifecycleTextColor` in `lib/turnaround.ts`. Palette: prewarn1=yellow, prewarn2=orange, prewarn3=red, breach1=light blue, breach2=grey, breach3=black, na=faded/hatched (display-only — independent of the fixed ageing scale; colours never affect thresholds). **Warning Parameters page** has a **Pre-warnings card ABOVE the grace/breach card**: per-activity PW1/PW2/PW3 percent inputs (global rows in "All Projects" mode; sparse inherited overrides in project mode, with "inherit" links) + an out-of-order warning + a global **stalled-days** input. Consumers: `status-dot.tsx` (lifecycle dot + optional stalled badge), `turnaround-warnings.tsx` (8-state phase summary + full strip + pre-warn/breach legend + per-activity bars + over-target drill), Overview `pages/overview.tsx` **"Needs attention" worklist** (breached + final pre-warning + stalled, via `useStalledInfo`, respects filters), `reports.tsx` adds export/table columns Consumed % / Days to Target / Lifecycle Status / Stalled. All consumers defensively `migrateTurnaroundSettings` before classifying.

## Parsing rules (parse.ts)

- Reads `Sheet1` (falls back to first sheet); reads all 19 columns (col S "Last Production Entry Date" is the 19th).
- **Header row auto-detected:** scans the first ~10 rows for the one containing `Project Code`; data starts on the next row. Falls back to the 3rd row (historical layout) with a problem note if not found.
- **Conditional `Project Code` forward-fill.** A blank Project Code is only a "continuation of the structure group above" for rows whose `Order Nature` is `Structure` (case-insensitive) — those inherit the last seen project. Project-less item types (`RSJ POLE` / `EARTHING` / `GENERAL`) and rows with a blank/unknown Order Nature have a genuinely empty project and must NOT borrow one from an adjacent row; they are stored under `job = "(Unassigned)"` (a constant in parse.ts) so the existing UI groups/filters them as their own selectable group without dashboard changes. A leading Structure row seen before any project code also falls through to `(Unassigned)` rather than a silent empty job. `(Unassigned)` is excluded from `projectsFound`. For these rows the value fed to mark derivation is empty, so their `markId`/`markNumber` stays the bare m_no (e.g. `"1"`) and never embeds a borrowed job. Since `job` participates in the row hash, rows previously mis-attributed will re-hash once and show as an attribution correction in the next diff (expected). Normalizes `"794."`→`794`, `"920.0"`→`920`.
- Keeps only rows with a non-empty `Mark No.`.
- **Mark No. → derived fields (VTPL consolidated Rules A–D, applied in this order; see `deriveMark` in parse.ts).** `project` is always col A; `mNo` is always kept whole (never split off variant letters like `X`/`R`/`RH` or trailing tokens like `R-4`). The separator in `markNumber` is `" \ "` (space-backslash-space):
  - **Rule A — bare mark:** col H has no space/backslash AND col A & col G are both empty (Earthing/General/RSJ Pole). `mNo = H`; `structure`/`proMno` empty; `markNumber = mNo` (may be non-numeric).
  - **Rule B — IS/SC/S rows ONLY** (col G is exactly `IS`/`SC`/`S`, case-insensitive): the only rows that get a `proMno` and a **4-part** `markNumber` = `project \ proMno \ structure \ mNo`. Strip the `"<A> <G>-"` prefix; strip a leading `VT` only when it sits directly before the inner project digits (`VT837`→`837`; `VT` inside `3IVTS`/`2CVT` is preserved); absorb an inner numeric project token into `proMno` (`IS-775`, `SC-775`, `IS-824.`) else `proMno = "<G>"`; then `structure` = first token (split on first `\`/`-`/space), `mNo` = the rest.
  - **Rule D — backslash form, non-IS/SC:** `structure` = segment before the LAST `\`, `mNo` = after it. **3-part** `markNumber` = `project \ structure \ mNo`.
  - **Rule C — standard space form `<A> <G>-<mNo>`, non-IS/SC:** strip the `"<A> <G>-"` prefix; `structure` = col G, `mNo` = remainder kept whole (do NOT split on the first dash — the alias itself can contain a dash, e.g. `2DF-5`). **3-part** `markNumber`.
- Legacy fields are aliases: `structure`=aliasCorrected, `markTail`=mNo, `markId`=markNumber. `proMno` is a new stored+API field (empty for non-IS/SC). `projectSuffix` is legacy/deprecated (always `""` under the current parser). Change-log identity = `markId|jobCardNo`. **NOTE:** because the `markNumber` format changed (new `" \ "` separators + Rule B 4-part marks), the first upload after this change will show widespread "completed + new mark" churn in the diff vs older imports — this is a one-time re-identification, not data loss (pool rows are keyed by the source-row hash, which is unaffected).
- `hash` is SHA-256 over the **original 19 source columns ONLY** (incl. col S "Last Production Entry Date"; derived mark fields excluded), so cleanups that touch derived fields don't change identity. (Adding col S to the hash is the one-time re-identification noted in Architecture decisions.)
- NO within-file dedup: every kept row becomes a pending unit; the `hash` dedups across uploads only.
- Ageing color scale (used everywhere): green ≤30, amber 31–60, red >60, neutral when no date.

## Upload: direct vs staged gatekeeper flow

- **Direct:** `POST /imports` parses, merges, and commits in one step (no gate). Still available.
- **Staged (gatekeeper):** `POST /imports/stage` holds the raw file in `upload_staging` (bytea) and returns a structural read; `POST /imports/validate` runs the Claude gatekeeper (verdict `ok`/`reject` + descriptive-only sanitize suggestions, `available:false` when no key); `POST /imports/commit` applies accepted `(field,from)→to` cleanups over the staged rows, re-hashes, then merges. `DELETE /imports/stage/{id}` discards. **Nothing is written to `record_pool`/`import_rows`/`imports` until commit.**
- **Commit is idempotent.** A successful commit does NOT delete the staged row; it marks it with the created import id (`upload_staging.committed_import_id`). A duplicate/retried commit (e.g. a slow ~10s commit that the deployment proxy retries on timeout) returns the same import with HTTP 200 (reconstructed `ChangeSet` from the stored `changeSummary`) instead of a misleading `404 "Staged upload not found"`. True concurrency is also safe: both commits serialize in `mergeImport`'s advisory lock and create imports, but only one wins the atomic claim (`UPDATE ... WHERE committed_import_id IS NULL`); the loser deletes its orphan import (cascades `import_rows`; pool untouched) and returns the winner. Committed staged rows are cleaned up by the 24h TTL (`expireStagedUploads`); `DELETE /imports/stage/{id}` still discards immediately. **Note: the `committed_import_id` column must exist in the production DB too — run `pnpm --filter @workspace/db run push` against prod after deploying.**
- Both paths share `mergeImport()` in `routes/imports.ts`. Accepted cleanups are remapped onto the base 19 source fields BEFORE hashing; mark identity is untouched. The gatekeeper is advisory only — it never mutates computed fields; the engine stays authoritative. UI is `staged-upload-panel.tsx` (wired into the Data view).

## Product

Five views: Overview (KPIs + "Changes since last upload" panel + ageing breakdown + top aged / busiest contractors), Activity (process-ordered activity cards with expandable mark tables), Ageing (buckets + activity-wise ageing table + full pending table), Contractor (workload bars + contractor×ageing matrix), Data (upload, parse summary, import list with change counts, CSV/JSON export). The Changes panel shows chips + a tabbed table (Moved activity / Qty-Wt changed / New marks / Completed) and a compare-any-two-imports selector. Cascading Job→Structure→Mark filters plus contractor/activity/search apply across all views.

## Gotchas

- **Large responses must be compressed.** The `/imports/{id}/records` endpoint returns the full expanded dataset (~28 MB+ JSON for a real report). The deployment proxy silently returns `500` (empty body) to the browser for oversized upstream responses even though the app logs `statusCode 200` — this surfaces as a misleading "No data for the selected filters" in the published app while dev works fine. `app.use(compression())` (in `artifacts/api-server/src/app.ts`) gzips it ~10x to stay under the limit. Keep compression enabled.
- After editing `lib/api-spec/openapi.yaml`, run `pnpm --filter @workspace/api-spec run codegen` before relying on hooks/schemas.
- After changing DB schema, run `pnpm --filter @workspace/db run push`.
- Tailwind v4: do not `@apply` a custom utility class; use raw CSS properties for things like `font-variant-numeric: tabular-nums`.
- React Query hooks need an explicit `queryKey` in `query` options (e.g. `getGetSnapshotRecordsQueryKey(id)`).
- **Activity ordering is centralized in `@workspace/domain` (`lib/domain`).** Never add a local `PROCESS_ORDER`/`ACTIVITY_ORDER` array or sort activities alphabetically — always use `compareActivity`/`sortActivities`. This is a display/ordering concern only; it must never change parsing, Activity values, quantities, ageing, or dedup. `unknownActivityCodes` in the AI review signals is internal (prompt-only), not part of the OpenAPI/Zod response schema — adding to it needs no codegen.
