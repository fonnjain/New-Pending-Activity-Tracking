## Two checks before approving

**1. Does the diff create a replacement CHECK constraint, not only drop the old one?**

If the old constraint goes and no new one arrives, `status` becomes unconstrained. Not dangerous,
but not what was intended — the point of the constraint is that a typo cannot enter the column.
The replacement should permit exactly `open`, `explained`, `superseded`.

**2. Does the replacement unique index cover the same column set as the constraint it replaces?**

A narrower set would reject rows that are legitimate today. A wider set would permit duplicates
the constraint currently prevents. Paste both definitions side by side.

**If both replacements are present and equivalent — approve the publish.**

**If either drop has no matching create — stop again and report.** That is a different situation
from the one I am authorising here.
