TASK: Add a "Net Balance Movement" tabular view to the Contractor Wise page, mirroring the one
being added to the Activity Wise page. Two measures per contractor per day: PRODUCED and NET
CHANGE. The app already holds 20+ days of consecutive imports.

=====================================================================
THE COLUMNS
=====================================================================
For each contractor, between consecutive imports (previous -> current):

  1) PRODUCED (MT) — real output. Mark-level, computed as:
        completed = sum of PREVIOUS Balance Wt for that contractor's marks that are NO LONGER
                    in WIP in the current snapshot (fully produced, so they dropped out)
        reduced   = sum of (previous Balance Wt - current Balance Wt) for that contractor's
                    marks still present AND still with the SAME contractor, whose weight
                    DECREASED
        PRODUCED  = completed + reduced

  2) RECEIVED (MT) — marks REASSIGNED IN from another contractor:
        sum of CURRENT Balance Wt for marks present in both snapshots whose contractor CHANGED
        to this contractor.

  3) RELEASED (MT) — marks REASSIGNED OUT to another contractor:
        sum of PREVIOUS Balance Wt for marks present in both snapshots whose contractor CHANGED
        away from this contractor.

  4) NEW INTAKE (MT) — marks appearing in the current snapshot that were not in the previous
        one, attributed to their current contractor.

  5) NET CHANGE (MT) — workload movement, simple aggregate:
        NET = total balance weight for this contractor now
            - total balance weight for this contractor in the previous snapshot
     Positive = workload growing; negative = workload clearing.

Key each mark by (normalized project Col B, structure Col J Alias, Mark No Col K).
Contractor = WIP Col D; a blank contractor is its own row labelled "(Unassigned)".
Scope TLT (Order Nature Col C = "Structure"), each row's own project code (no forward fill).
Col Q is KG — divide by 1000, present MT to 3 dp.

RECONCILIATION (verified exact on 19->20 Jul, zero failures across all contractors):
        Net = -Produced + Received - Released + New Intake + Increases
where "Increases" is same-contractor weight going UP (corrections). Use this as an internal
assertion: if a contractor's columns do not satisfy it, the calculation is wrong.

=====================================================================
CRITICAL — WHY "PRODUCED" IS NOT THE SAME AS "NET CHANGE"
=====================================================================
Marks are REASSIGNED between contractors constantly, and that movement is far larger than
actual production. VERIFIED 19-Jul -> 20-Jul, whole file:
        reassigned IN    298.14 MT
        reassigned OUT   273.36 MT
        completed         60.08 MT
        reduced           84.61 MT
        new intake        54.70 MT
Reassignment is roughly 3x actual production (145 MT). A net figure alone is therefore
MISLEADING: it mostly reflects work being handed between contractors, not work being done.

Worked example — UNIT-II on 20-Jul:
        NET CHANGE = +31.1 MT   (looks like a bottleneck / work piling up)
        PRODUCED   =  51.2 MT   (13.49 completed + 37.72 reduced — a highly productive day)
The net is positive only because UNIT-II was GIVEN 97.11 MT of reassigned work while releasing
37.69 MT. Showing net alone would completely misread this contractor's performance.

THEREFORE, when computing PRODUCED:
  - EXCLUDE marks whose contractor CHANGED between snapshots. A mark leaving contractor X for
    contractor Y is NOT production by X, and its arrival is NOT production by Y. That movement
    belongs in the Released / Received columns instead.
  - EXCLUDE new marks appearing in the current snapshot — they belong in New Intake.
  - EXCLUDE weight INCREASES (corrections), never negative production.
  - Only same-contractor weight reductions, plus marks that genuinely left WIP, count.

The Received and Released columns EXIST PRECISELY SO THIS IS VISIBLE. Without them a user
cannot explain why UNIT-II's net is +47.01 while it produced 51.21 — the answer (97.11 in,
37.69 out) must be on screen.

=====================================================================

day), do NOT present a multi-day delta as one day's figure — it would show a false spike.
Either omit missing days, label the span with its elapsed days ("18-20 Jul (2 days)"), or show
a per-day average clearly marked as averaged. Use the import's own date (or WIP file date) as
the day key, not the upload timestamp. If only one import exists, show "-", not zero.
