=====================================================================
DIAGNOSIS CONFIRMED (verified against the source files)
=====================================================================
Root cause = structure-name mismatch between the WIP parser and the Order Review parser.
Verified independently:
  - Project 946: all 19 OR structures carry a LEADING DASH ("-069-2NBA1" ...) while WIP has
    them without ("069-2NBA1"). ~97% of Unknown weight. FIXABLE.
  - Project 920: OR stores "4TA/4TB/4TC/4TD/4TE/4TF" and "CBOM"; WIP parses "TA/TB/TE/TF"
    and "CBOM-920\2CE". Tiny (0.051 MT). This is a genuine SOURCE-FILE naming inconsistency.
  - 168 header-row leak rows (structure = "Project Code : NNN") pollute order_review_rows.

=====================================================================
FIX 2 — APPROVED (do first): skip Order Review header-row leakage
=====================================================================
In the Order Review parser, SKIP any row whose structure/Tower-Type cell (Col C) begins
with "Project Code" — these are project-banner rows, not structures. They must never be
stored in order_review_rows. This removes the 168 phantom rows (and the "Project Code : 946"
row that falsely made 946 look present). Purely additive; only the OR parser changes.

=====================================================================
FIX 1 — APPROVED WITH A GUARD: strip a leading dash from OR structure codes
=====================================================================
After extracting the structure code from Col C, strip a SINGLE leading "-" before storing,
so OR "-069-2NBA1" matches WIP "069-2NBA1". BUT add this guard (the blind replace is unsafe):

  *** DO NOT strip if the code is ALL dashes or would collide. ***
  Reason: project VR082 contains junk placeholder structures literally named "-", "--",
  "---", "----". Stripping one dash turns "----" into "---", which already exists → key
  collision and data corruption.

Implement safely:
  - Only strip the leading dash if, after stripping, the result is NON-EMPTY AND contains at
    least one non-dash character (i.e. skip codes that are entirely dashes).
  - After stripping, if the resulting structure code already exists for the same project
    (collision), do NOT merge — keep them distinct (e.g. leave the dashed one as-is) and log
    it. Never silently collapse two different structures into one.
  - Apply ONLY in the OR parser, mirroring what the WIP parser already does to its Alias.
    Idempotent: codes without a leading dash are unchanged.

Expected effect: project 946's 19 structures now match WIP and resolve to their real BOM
Label ("Proto"), collapsing the ~98.8 MT Cutting / ~2.08 MT QC out of "Unknown" into the
correct label. VR082 junk rows remain unchanged (no collision).
