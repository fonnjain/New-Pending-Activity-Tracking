## PART 1 — a blocking guard: cumulative despatch must never decrease

**This is not hypothetical. Today's files trip it.**

The 24-August exports arrived scoped down. The Order Review fell from **166 projects to 117** and
2,267 rows to 1,734, and on eighteen projects the cumulative despatch figure **went down**:

```
project   despatched 22-Aug   despatched 24-Aug
VS-68            966.931 MT           0.000 MT
918              534.392 MT           0.000 MT
931              481.179 MT           0.000 MT
882              464.158 MT           0.000 MT
775              417.889 MT           0.000 MT
```

Cumulative despatch cannot fall. Material does not un-ship. Those projects were removed from the
export, not reduced.

The WIP file matches: **92 projects down to 67**, with 26 gone carrying **955.479 MT**, almost all
of it finished goods — 775 at 387.473 MT entirely FG, 837 at 229.020 MT entirely FG. The 66
projects present on both days moved **−23.296 MT**, a completely normal day.

### Why this must block rather than warn

`order_review_rows` upserts one row per project and structure. A project absent from the incoming
file **keeps its previous row untouched**. So importing today's file would leave the table holding
22-August figures for the 49 missing projects and 24-August figures for the rest — two different
days in one table.

Nothing would look broken. The totals would still foot. Every report drawn from it would be
quietly wrong and no screen would show it.

### The rule

At **staging**, before anything is written, compare the incoming Order Review against the current
latest Order Review import:

```
For each project present in BOTH files:
    if incoming Progress Despatch < stored Progress Despatch  -> BLOCK

For each project present in the STORED file but absent from the incoming file:
    if stored Progress Despatch > 0                           -> BLOCK
```

Report every failing project by name with both figures and the difference. Refuse the import — no
override, no "proceed anyway". A file that fails this test is the wrong file, not a malformed one.

Apply the same test to **Progress Release**, which is also cumulative, but report it as a warning
rather than a block until we have seen it fire once.

### Also add, as a loud warning rather than a block

```
Order Review project count   +/- 5 projects
Order Review data rows       +/- 10%
WIP project count            +/- 3 projects
WIP total weight             +/- 5%
any WIP bucket               +/- 10%
NTLT mark count reaching zero
```

Show each as `previous -> new (change)`. A number alone cannot be judged; the person clicking
Import needs both sides. Staging 24-August against 23-August should light up several of these.

### First import of a kind

Where there is nothing to compare against, say so plainly rather than showing a delta against
zero.
