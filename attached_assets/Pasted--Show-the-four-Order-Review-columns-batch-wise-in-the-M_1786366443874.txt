# Show the four Order Review columns batch-wise in the MFC views

In the MFC-grouped Project Wise views, Work Order Qty, Dispatch Qty, Dispatch Balance and
FG (Order Review) currently render as `—` on every batch row. This changes them to real
figures that sum to the project row.

## FIRST — a correction to the earlier analysis

An earlier assessment concluded that ~80 structures span more than one batch and that any
mapping would therefore be guesswork. That count treated **Z as a batch**. It is not — `Z` is
this app's own sentinel for a blank `Batch No.`; the WIP file contains only A, B, C, D and
blank. Every `{A, Z}`, `{B, Z}`, `{C, Z}` pairing is one real batch plus marks that have not
been stamped yet, not two batches.

Measured on the 10-Aug file, all 882 TLT structures:

```
465  one real batch, no unbatched marks
 82  one real batch + some unbatched marks
334  every mark unbatched
  1  two real batches  -> 920 / 3LISO  (C: 11 marks, D: 61 marks, 1.610 MT)
```

3LISO is the only genuine multi-batch structure, and it is the only one on 11-Jul, 21-Jul,
24-Jul, 01-Aug, 05-Aug, 08-Aug and 10-Aug alike. The ambiguity the earlier assessment was
worried about is worth 2.242 MT of Work Order out of 27,131.073.

Note also: `Batch No.` is **column X** of the WIP file, not column U. Column U is
`Ref. Job Card No.`.

## THE RULE

Build a structure → batch map from the WIP marks **of that import** (from `import_rows`, not
from `record_pool` — see the guard below). For each Order Review structure:

| Case | Goes to |
|---|---|
| Its WIP marks carry exactly one real batch letter (blanks allowed) | that batch row |
| Every one of its WIP marks is unbatched | the `Z` row |
| It has no WIP marks at all | a new **No pending balance** row |
| It has two real batch letters (920 / 3LISO only) | the `Z` row |

Apply this to the four Order Review columns **only**: Work Order Qty, Dispatch Qty, Dispatch
Balance, FG (Order Review).

## WHAT TO CHANGE

1. Populate those four columns on batch rows using the rule above.
2. Add one row type per project, labelled **No pending balance**, carrying only the four Order
   Review columns. Its WIP columns are blank — those structures have no pending marks by
   definition.
3. In the MFC export, the TOTAL row must show the true project totals for those four columns.
   It currently emits `0`, which is a false statement — 27,131.073 / 14,380.689 / 12,750.384 /
   4,618.594 MT are the correct 10-Aug values.
4. Render a true zero as `0.0t`, not `—`, so "this batch has none" stops looking identical to
   "not applicable here".

## WHAT NOT TO CHANGE

- Do NOT change the seven WIP-derived columns. Release Balance Computed, Awaiting Assignment,
  Cutting, Quality Check, Galvanising, FG (WIP file) and Total stay **per-mark**: a mark
  stamped A counts in A, a mark left blank counts in Z. They currently reconcile exactly to
  the source file and must continue to.
- Do NOT reassign blank-batch marks to their structure's batch in the WIP columns. That would
  move 1,080 marks / 83.133 MT out of Z and break the reconciliation above.
- Do NOT pro-rata, apportion or estimate any Order Review figure across batches. Every figure
  must be a whole structure's value sitting in exactly one row.
- Do NOT change parsing, hashing, dedup, the bucket definitions, ageing, activity, milestones
  or dispatch logic.
- Build the structure → batch map **per import**. A map keyed off `record_pool` would inherit
  the retroactive-corruption pattern that `job_card_status` had: a mark stamped between
  uploads would retrospectively move Order Review weight between batch rows on every earlier
  import. The per-mark `batchKey(project, structure, mfcBatch)` helper in
  `fabricationProjectCompletion.ts` is the right primitive to reuse.

## ONE THING TO FLAG, NOT FIX

Coverage is uneven and users need to see it. Across all 65 projects, the share landing on a
real batch letter is 49.0% of Work Order, **19.5% of Dispatch** and 86.3% of FG (Order
Review). Dispatch is dominated by the Z and No-pending-balance rows, because material that
has shipped completely leaves the WIP file and takes its batch letter with it. That is a
source-data limit, not a bug — the only real fix is adding a `Batch No.` column to the Order
Review export template. Do not attempt to close the gap in code.
