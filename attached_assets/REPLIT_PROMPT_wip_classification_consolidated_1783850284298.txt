=====================================================================
CHANGE 1 — Order Nature is the SOLE TLT/NTLT classifier
=====================================================================
Define classification EXACTLY as:
    TLT   <=> Order Nature (Col C) == "Structure"
    NTLT  <=> Order Nature (Col C) in {"RSJ POLE", "EARTHING", "GENERAL"}
Trim + case-insensitive compare. No other rule, no fallback, no subtype-string parsing, no
inference from activity codes. It is exact, mutually exclusive and exhaustive.

- Replace any existing TLT/NTLT derivation that uses subtype strings, "_NTLT" tags, activity
  sets, or heuristics with this single rule, in ONE helper (e.g. classifyOrderNature(row)).
- If a future file contains an Order Nature value outside these four, do NOT guess: flag it
  in the upload sanity check as "unknown Order Nature — classification undefined" and treat
  it as NTLT (safe default: keeps it out of TLT reports) until the user classifies it.
- Keep the existing per-line sequences as-is (TLT sequence; NTLT_RSJ; NTLT_EARTHING/GENERAL).
  This change only fixes HOW a mark is assigned to a line.

=====================================================================
CHANGE 2 — REMOVE project-code forward-fill (CRITICAL BUG)
=====================================================================
WIP Col B (Project Code) is FULLY POPULATED on every TLT row (57,525/57,525). Forward-filling
the project code from a previous row is WRONG and actively corrupts data.

*** If the WIP parser forward-fills Col B (e.g. carrying the last seen project down through
rows where Col B is blank), REMOVE IT. ***

Why this is critical: the ONLY rows with a blank Col B are the 282 project-orphaned NTLT rows.
A forward-fill glues those orphans onto whatever project happens to precede them in the file,
silently inflating that project's totals. Verified example: forward-fill wrongly attributed
221.6 MT of RSJ POLE finished-goods weight to project 862, which has NO RSJ POLE rows at all.
Orphan FG weight alone is ~597 MT; total orphan NTLT weight is ~6,140 MT.

Read Col B directly. A blank Col B means "no project", NOT "same project as the row above".

CHANGE 3 — Handle project-orphaned NTLT rows explicitly
=====================================================================
282 rows (RSJ POLE 245, EARTHING 21, GENERAL 16) have NO project code at all — ~6,140 MT
total, including ~597 MT of "FG Pending For Dispatch" weight.

Required behaviour:

- Attribute them to an explicit "(No Project)" bucket so the weight is not silently lost,

- They are NTLT, so they must NOT appear in any TLT-filtered report (project-wise TLT report,

- Surface a count + weight of orphan rows in the upload sanity check, e.g. "282 NTLT rows have
  no project code (~6,140 MT) — attributed to (No Project), grouped by Section". This is a
  data-quality signal worth showing, not hiding.

CHANGE 3b — NTLT IDENTITY: Section (Col L) is the key
=====================================================================
NTLT rows have NO project and NO structure. Verified across all 282 NTLT rows:
    Col B (Project Code)  : 100% BLANK
    Col J (Alias/Structure): 100% BLANK
    Col H (Tower Type)    : 100% populated
    Col L (Section)       : 100% populated

Therefore NTLT CANNOT be keyed by (project, structure) — that key is null for every NTLT row.
Any join/grouping that assumes project+structure will silently produce nulls or drop all 282
NTLT rows. NTLT also cannot join to Order Review at all (Order Review is organised by
project+structure), which is why NTLT weight has no order-book counterpart. That is expected,
not a bug.

*** THE NTLT KEY IS SECTION (Col L), ALONE. ***
    NTLT identity = Section (Col L)
Verified sufficient: 38 distinct Sections cover all 282 NTLT marks / 6,140.238 MT, and ZERO
Sections span more than one Order Nature — each Section belongs unambiguously to exactly one
of RSJ POLE / EARTHING / GENERAL. So Section alone cleanly implies its NTLT line.

Do NOT compound the key with Tower Type. Keep it simple: Section is the identity.

Group/report NTLT by Section. Within the "(No Project)" bucket (CHANGE 3), sub-group by
Section — that is the only meaningful NTLT breakdown available. For scale, RSJ POLE dominates:
    RSJ 152X152X12 - [37.1]   38 marks  1405.496 MT
    RSJ 152X152X11 - ([37.1)  71 marks  1350.403 MT
    RSJ 152X152X13 - [37.1]   17 marks  1124.724 MT
    RSJ 152X152X16 - [37.1]   28 marks   558.578 MT
    ... 34 more sections ...  TOTAL 282 marks / 6140.238 MT

TOWER TYPE (Col H) = VERIFICATION ONLY, never part of the key.
Use it as a cross-check: each Section should map to exactly ONE Tower Type. Section is
essentially Tower Type restated as a material spec (the "HDG" prefix dropped, dimensions
carried over, "MS" appended) — e.g. "HDG RSJ POLE 203X203X13" -> "RSJ 203X203X13";
"HDG FLAT 75X12" -> "FLAT 75X12 MS".
37 of 38 Sections map 1:1 to a Tower Type. Flag the mismatches in the upload sanity check as
a DATA-QUALITY warning (do not block, do not auto-correct):
    KNOWN MISMATCH (1): Section "RSJ 152X152X10 - [37.1]" maps to TWO Tower Types —
    "HDG RSJ POLE 152X152X10 - 37.1kg" AND "HDG RSJ POLE 152X152X5 - 37.1kg"
    (Tower Type says thickness 5, Section says 10 — an ERP contradiction, 2 marks ~14.5 MT).
Also worth flagging if seen: Tower Types whose Section drops or contradicts the thickness
(e.g. "HDG PLATE 6MM" -> "PLATE 12 MM MS"; "HDG RSJ POLE 160X152X13" -> "RSJ 160X160X13").
These are source-data errors for the ERP team, surfaced not fixed.
