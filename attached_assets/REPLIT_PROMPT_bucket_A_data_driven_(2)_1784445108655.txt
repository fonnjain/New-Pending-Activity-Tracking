=====================================================================
CHANGE 1 — Bucket A membership is now derived, not entered
=====================================================================
Bucket A = every PROJECT in the Order Review file where BOTH are true:

        WO Order Qty Weight   (Order Review Col J)  ==  0
    AND Progress > Release    (Order Review Col L)  ==  0

Meaning: the order exists in the book, but no work order has been raised and nothing has been
released to the shop. It has not started.

Grain: PROJECT level (one row per project), matching how Bucket A is presented today.

A project LEAVES Bucket A automatically as soon as either a work order is raised (Col J > 0)
or any release progress appears (Col L > 0). No user action, no flag, no stored state —
membership is recomputed from the file on every import.

Use a small tolerance for the zero test (e.g. abs(value) < 0.001) to avoid float noise.

=====================================================================
CHANGE 3 — MFC on transition OUT of Bucket A (into B/C/D)
=====================================================================
The "Z" in Bucket A is a CONSTANT only while the project sits in Bucket A. The moment a
project becomes eligible to leave Bucket A (a work order is raised, Col J > 0, or release
progress appears, Col L > 0), it stops being a Bucket A row and is evaluated by the normal
B/C/D rules — and from that point its MFC batch MUST be looked up from WIP like every other
bucket structure, NOT carried over as a hard-coded "Z".

Required behaviour once a project leaves Bucket A:
  - Apply the standard structure -> MFC batch assignment used by B/C/D:
        if any of the structure's WIP marks has a real batch (A/B/C/D) -> that batch
        if all its marks are blank                                     -> "Z" (Not Yet Batched)
        if 2+ real batches                                             -> heaviest by balance weight
  - The project's rows then group under whichever real batches WIP reports. A project can span
    several batches at once — that is normal and expected.
  - Nothing is stored or cached. MFC is re-derived from WIP on EVERY import, so a project that
    is "Z" today automatically shows A/B/C/D as soon as the shop batches its marks. There must
    be no manual step and no persisted batch value.

Expected shape of a just-transitioned project: it will typically be ALL "Z" at first (WIP marks
now exist, but the shop has not batched them yet), then progressively shift to real batches.
VERIFIED on current data — of the 28 projects already in Bucket B:
    12 are ALL Z  (807, 885, 890, 908, 910, 914, 937, 946, 948, 958, 960, VS-33)
     5 are partly batched (900, 912, 917, 938, 944 — a mix of Z and real batches)
    11 are fully batched (824, 920, 926, 928, 929, 933, 934, 935, 939, 940, 942)
This is the natural lifecycle: Bucket A (Z, no WIP) -> Bucket B all-Z (WIP exists, unbatched)
-> partly batched -> fully batched. Do not treat the all-Z state as an error.

IMPORTANT: do not special-case "projects that came from Bucket A". There is no transition
event to handle and no state to migrate — membership and MFC are both recomputed from the
files each time. A project simply stops matching the Bucket A rule and starts matching B/C/D.
