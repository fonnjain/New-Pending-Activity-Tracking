## Why these three buckets are common to TLT and NTLT

Release, Assignment and Cutting key only on **Type (Col A) + Job Card Status (Col G) +
Contractor (Col D)**. None of them touches Activity or Order Nature.

Activity is the *only* dimension that differs between the two natures:

| | TLT | NTLT |
|---|---|---|
| Not Started activities | `C` | `BL, NTF, NTFSW, G, TS` |
| Job Card WIP activities | `B, G, GB, HAB, NH, Q, RFI, TS, W, Y` | `G, GB, TS, Y` |
| FG activities | (blank) | (blank) |

That divergence is exactly why the old activity-based Cutting rule returned **zero** for
NTLT. Keying on Type + Status makes all three buckets nature-agnostic by construction, and
the five-bucket model then partitions both natures with zero unclassified marks.

## Which rules are enforced, and which are merely observed

Worth keeping in mind when deciding how hard to fail on a violation.

**Almost certainly ERP-enforced** — semantically necessary, and they hold identically
across both order natures: U1, U2, U3, U4, U5, U6, U7. You cannot have work in progress on
an unauthorised job card, so the state machine
`Not Started/Initial → Not Started/Authorized → WIP/Authorized → FG/Authorized` is
structural. Only four of six possible Type × Status combinations ever occur.

**Process facts, true for TLT but not universal:** T1 above all. It is false for NTLT.
Treat these as scoped assertions, never as general invariants.

**Business-process conventions that could change:** T4 (Initial implies blank contractor)
holds because assignment happens at or after release. If the ERP ever permits
pre-assignment this breaks — which is exactly why it belongs in the ERP tab as a monitored
rule rather than as a filter condition inside Release Balance.
