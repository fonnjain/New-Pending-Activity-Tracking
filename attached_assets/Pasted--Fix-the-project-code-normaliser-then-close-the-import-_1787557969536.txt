## PART 1 — one of the five blockers is a false positive, caused by the normaliser

`RAILWAY` is not a project. The Order Review carries two separate blocks:

```
Project Code : RAILWAY BATCH 10
Project Code : RAILWAY BATCH 11
```

The project-code normaliser truncates at the first space, so both collapse into `RAILWAY`. On the
24-August file, batch 11 has been closed and batch 10 is unchanged:

```
RAILWAY BATCH 10   despatch  420.828 -> 420.828   unchanged
RAILWAY BATCH 11   despatch  149.340 -> ABSENT    closed
merged "RAILWAY"   despatch  570.168 -> 420.828   apparent -149.340 regression
```

Nothing regressed. A normal closure has been turned into a blocking regression by the merge —
**Test B misclassified as Test A**. The guard is behaving correctly on the data it was given; the
data was mangled before it reached the guard.

### The fix

In the project-code normaliser, **stop truncating at whitespace**. Keep the existing behaviour
that strips trailing dots and leading dashes — `907` and `907.` are genuinely one project, and
that merge must not change. But `RAILWAY BATCH 10` and `RAILWAY BATCH 11` are two distinct order
blocks and must stay separate.

Please state the current normaliser's exact transformation before changing it, so we can see what
else it affects. I first noticed this when a project count came back as 164 against my 165 and
treated it as cosmetic. It is not — it now produces a false blocker, and it will recur on any
project code containing a space whenever one of its batches closes.

Report the new absent-project count and total. Both will move by one project and by

Do NOT add a special case for `RAILWAY`. The fix belongs in the normaliser, not in the guard.
